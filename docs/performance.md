# Производительность FreeCut

Проверка и оптимизация от 15 октября 2026 года. Проверено на Apple M3 Pro,
18 GiB RAM, macOS arm64, Rust 1.99.0 и установленном FFmpeg 8.1.1.
Отдельный запуск CPU-only проверен на Linux arm64 с жёстким лимитом 1.5 GiB
памяти и квотой 2 CPU; среда и границы проверки описаны ниже.
Дизайн, монтажные операции, формат проекта, разрешение экспорта и алгоритмы
цветокоррекции сохраняются. Это замеры конкретной машины, а не минимальные
системные требования или обещание скорости на любом компьютере.

## Цель: 2 ГБ RAM и CPU-only

После уточнения целевой машины добавлен единый аппаратный бюджет
`freecut-media::resources`. Он считывает только RAM, учитывает cgroup-лимит
Linux и число доступных CPU. Компактный режим включается при RAM до 4 GiB,
неизвестном размере RAM, `--low-memory`, `--software` или
`FREECUT_LOW_MEMORY=1`. Политика общая для превью, экспорта и плиток.

| Ресурс | Обычный режим | Компактный режим |
|---|---:|---:|
| Общий пул пиксельных работников | до 8 | до 2 |
| FFmpeg frame threads на декодер | до 4 | 1 |
| Декодеры, если рабочих источников в кадре меньше лимита | 4 | 1 |
| Фоновые работники приложения | 2–4 | 1 |
| Кеш graded source/output, на композитор | 64 MiB | 8 MiB |
| Mip-кеш, на композитор | 64 MiB | 8 MiB |
| Кеш размытия, на композитор | 96 MiB | 8 MiB |
| Текстовые растры, на композитор | 64 MiB | 8 MiB |
| Анимированные растры, внутри текстового бюджета | 16 MiB | 2 MiB |
| Глифы, на композитор | 32 MiB | 4 MiB |
| Текстуры filmstrip | 64 MiB | 8 MiB |

Ограничивается удержание результатов; вычисляемый сейчас кадр и активные
слои не теряют разрешение или точность. Большой результат, не помещающийся
в кеш, возвращается без сохранения в нём. Это не жёсткий лимит всего процесса:
документ, исходные изображения, LUT, пики звука, шрифты, рабочие буферы и
драйвер также занимают память.

Видео уже компонуется CPU. Для всего оконного интерфейса на CPU используется
программный адаптер wgpu. `--software` принимает только адаптер типа `Cpu`,
совместимый с окном, и сообщает ошибку, если его нет. Выбора аппаратного GPU
в этом режиме нет. Такой путь требует программного графического драйвера:
Mesa lavapipe на Linux или WARP на Windows. См. описание
[software/fallback adapter в wgpu](https://docs.rs/wgpu/30.0.1/wgpu/struct.RequestAdapterOptionsBase.html)
и [типов адаптеров](https://docs.rs/wgpu/30.0.1/wgpu/struct.AdapterInfo.html).

```sh
# Обычное окно, малые бюджеты памяти
cargo run -p freecut-app --release -- --low-memory
# Окно через программный адаптер, также с малыми бюджетами
cargo run -p freecut-app --release -- --software
```

На проверяемом Mac программного адаптера, способного показать окно, нет:
`--software` корректно завершился с объяснением. GPU-режим с компактными
кешами запускается. CPU-only на macOS этой проверкой не подтверждён.

## Где расходуются ресурсы

| Участок | Когда нагружает CPU / память | Что изменено |
|---|---|---|
| CPU-композитор | Каждый кадр превью и экспорта: семплирование, преобразования, смешивание | Кадры с целочисленным смещением и масштабом 1:1 идут напрямую по пикселям, с тем же смешиванием alpha. Остальные используют прежний алгоритм |
| Потоки рендера, цветокоррекции и размытия | Раньше создавались и завершались заново для каждого прохода | Общий пул максимум из 8 работников, ограниченный числом доступных CPU. Маленькие задания выполняются на вызывающем потоке. При невозможности создать пул остаётся последовательный путь |
| Заголовок окна | Его повторная отправка в ОС на каждом UI-кадре вызывала лишние перерисовки, в том числе на Home | Отправляется только при изменении текста |
| Окно при воспроизведении | Раньше таймер каждые 5 мс, даже для проекта 24/30 fps | Следующее обновление назначается на границу кадра проекта; звук остаётся главным источником времени. Ввод и готовые фоновые результаты по-прежнему будят окно сразу |
| Аудиопоток на паузе | Раньше опрос каждые 4 мс, до 250 пробуждений/с | Ожидает команды, событие устройства или точный срок повторного открытия. Активное воспроизведение сохраняет прежний опрос кольцевого буфера |
| Входы превью | Каждый запрос копировал пути медиа и список offline, заново строил таблицу файлов | Общий неизменяемый снимок до изменения проекта/медиа; декодерам таблица передаётся только при изменении входов |
| Завершённые кадры превью | Неограниченная очередь могла расти, пока окно занято | Один слот с последним готовым кадром, независимо от числа обновлений |
| Видео и изображения | По декодеру с FFmpeg-буферами на каждый когда-либо просмотренный файл | LRU с обычным пределом 4. Если в кадре одновременно больше источников, сохраняется весь его рабочий набор, чтобы не открывать их заново каждый кадр |
| Кеш цветокоррекции | До 8 пар source/output; для 4K это около 506 MiB | Лимит 64 MiB по сумме удерживаемых RGBA source/output плюс прежний предел 8 записей (в компактном режиме 8 MiB). Одна пара сверх бюджета возвращается без кеширования |
| Mip-уровни | До 32 наборов без ограничения в байтах | Не более 64 MiB (8 MiB в компактном режиме) и 32 записей, с вытеснением давно неиспользуемых. Также исправлен выбор уровня при переходе обратно с грубого к более детальному |
| Поиск пиков и постеров | Обход всей медиатеки/клипов на каждом UI-кадре | Повторяется только при изменении ревизии проекта или медиа |
| FFmpeg avfilter | Загружался только ради запроса собственной версии | Зависимость удалена; эффекты и цветокоррекция FreeCut реализованы в собственном рендере |
| Release-файл | Символы и код на границах crate | Thin LTO и удаление символов. Оптимизация пиксельных циклов сохранена; привязки к CPU машины сборки нет |
| Старые GPU | Стандартный descriptor требовал 8192px текстуры и desktop-лимиты | Для UI используются downlevel-лимиты без compute/storage-требований, максимальный размер текстуры согласован с адаптером |

Числа в строках о таймерах — периодичность, установленная кодом, а не процент
общей загрузки CPU. Проценты CPU для всего приложения зависят от кодеков,
разрешения, числа слоёв и эффектов. Декодирование и экспорт могут занимать все
доступные ядра и после этих изменений.

## Размер проекта и приложения

Исходный замер рабочего каталога: около 60 GiB всего, из них 38 GiB `target/`,
около 10 MiB `crates/`, 12 MiB `assets/` и 300 KiB `resources/`. Размеры
приблизительные, сняты во время работы; кеш сборки после новых сборок растёт.
`target/` и история Git не входят в распространяемое приложение. Исходные кеши и история Git не удалялись. После проверок удалены только
6.33 GiB incremental-артефактов компилятора, созданных текущей работой;
готовые сборки и результаты тестов сохранены.

Исходный debug-бинарник: около 67 MiB. Для сравнения оптимизации отдельно
собрана исходная release-версия: 45 092 944 байта. Её несистемные динамические
зависимости Homebrew — ещё 38 112 304 байта (16 уникальных dylib).
Самые большие: avcodec 9.35 MiB, x265 7.22 MiB, libcrypto 4.65 MiB,
avfilter 2.91 MiB, SVT-AV1 2.77 MiB. Встроенные шрифты сохраняются.

Размер одного исполняемого файла не является размером готового установщика:
для распространения надо упаковать совместимые библиотеки FFmpeg.

## Измеренные результаты

Парные прогоны исходного и оптимизированного release-бенчмарка чередовались
три раза. В таблице медианы, миллисекунды на кадр. Это синтетический RGBA с
прозрачностью; декодирование и UI сюда не входят. Все контрольные суммы до
и после совпали. Хост используется и другими процессами, поэтому абсолютное
время может меняться.

| Сцена | Полосы | До, мс | После, мс | Ускорение |
|---|---:|---:|---:|---:|
| tile | 1 | 0.142 | 0.038 | 3.74x |
| tile | 4 | 0.077 | 0.038 | 2.03x |
| preview | 1 | 3.048 | 0.817 | 3.73x |
| preview | 4 | 0.948 | 0.295 | 3.21x |
| 1080p | 1 | 11.764 | 3.188 | 3.69x |
| 1080p | 4 | 3.236 | 1.048 | 3.09x |
| 4k | 1 | 47.431 | 12.961 | 3.66x |
| 4k | 4 | 13.752 | 3.774 | 3.64x |
| rotated-preview | 1 | 15.108 | 14.968 | 1.01x |
| rotated-preview | 4 | 4.718 | 4.615 | 1.02x |

Обычные кадры ускорились примерно в 3–3.7 раза; три повёрнутых слоя остались
почти на прежнем уровне. Это не множитель скорости всего экспорта: кодек,
звук, сложные эффекты и запись файла измеряются отдельно.

Release-файл: **43.00 → 38.03 MiB**, на **11.56% меньше**. Несистемные dylib
этой macOS-сборки: **36.35 → 32.73 MiB**, 16 → 14 файлов. Вместе это примерно
79.35 → 70.76 MiB до упаковки установщика; системные библиотеки сюда не входят.

В коротком парном замере простоя Home, после 18 с прогрева, исходная release
показывала 20.3–24.3% CPU, компактная release — 2.8–7.6% (три выборки `ps`,
без воспроизведения). В другой выборке компактная сборка показывала 0.0%.
Устранена повторная отправка заголовка окна и связанная с ней перерисовка;
потоки обработки данных в это время спят. Это наблюдения на macOS, не лимит
загрузки на всех ОС. `sample` показал физический footprint простоя
250.3 → 94.3 MiB; пиковый footprint запуска 252.5 → 322.4 MiB, то есть
пик старта не уменьшился. RSS в `ps` и footprint измеряют разные вещи.

Пять снимков интерфейса при `FREECUT_LOW_MEMORY=1` — Dark, Compact,
Home, hover разделителя и увеличенный Stage — совпали с исходными:
**0 изменённых пикселей**. Сравнивались декодированные RGBA, не PNG-файлы.

Сырые замеры, размеры, контрольные суммы и исходный commit записаны в
[performance-results.json](performance-results.json).

## Воспроизведение замеров

```sh
cargo build -p freecut-app --release --locked
cargo test -p freecut-render --release --test performance -- --ignored --nocapture
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

`performance` измеряет только CPU-компоновку заранее декодированного RGBA:
плитка, превью, 1080p, 4K и три повёрнутых слоя. Есть последовательный путь
и четыре полосы; маленькие кадры автоматически остаются последовательными.
Время включает подготовку и заполнение выходного буфера, исключает декодер,
загрузку GPU и вывод звука. Выводятся контрольные суммы; регрессионные тесты
сравнивают пиксели с общим shader-путём для прозрачности, обрезки и смещений.
Для сравнения нужны одна машина, одинаковые входы и несколько чередующихся
прогонов без параллельной компиляции. Временные пороги не блокируют обычный CI.

Снимки интерфейса можно проверить существующим тестом:

```sh
FREECUT_SNAPSHOT_ONLY=dark FREECUT_SNAPSHOT_DIR=/tmp/freecut-ui \
  cargo test -p freecut-app snapshots::main_window_snapshots -- --nocapture
```

- `cargo test --workspace -- --skip snapshots::main_window_snapshots` —

- `FREECUT_LOW_MEMORY=1 cargo test -p freecut-app e2e::` — 13 успешно.
- `cargo test -p freecut-audio --no-default-features` — успешно.
- `FREECUT_LOW_MEMORY=1 cargo test -p freecut-render --lib` — 121 успешно.

## Проверка CPU-only с лимитом 1.5 GiB

Release собран для Linux aarch64 в отдельном контейнере: Rust 1.99.0,
Debian trixie с пакетами unstable, FFmpeg 9.0.2-3, Mesa 26.2.4-1,
libxkbcommon и libxkbcommon-x11 одной версии 1.13.1-1. Сборка с одним
работником Cargo, отключёнными incremental и LTO прошла под жёстким лимитом
2 GiB без swap и OOM. Пик cgroup сборки — 1 347 432 448 байт (1.25 GiB).
Это отдельная проверочная Linux-сборка; размеры выше относятся к macOS
release с Thin LTO.

Само приложение проверялось с лимитом **1 610 612 736 байт (1.5 GiB)**,
без swap, с квотой 2 CPU и без сети. GPU-устройства не передавались,
`/dev/dri` отсутствует. Окно выводилось в Xvfb 1440×900. Запуск:

```sh
DISPLAY=:99 WGPU_BACKEND=vulkan LP_NUM_THREADS=2 \
  XDG_RUNTIME_DIR=/tmp/runtime \
  VK_DRIVER_FILES=/usr/share/vulkan/icd.d/lvp_icd.json \
  freecut --software
```

В логе подтверждён адаптер `llvmpipe (LLVM 22.1.8, 128 bits)`.
Через настоящий оконный интерфейс созданы проект 1920×1080 / 30 fps,
текстовый клип перетаскиванием на таймлайн, воспроизведение с видимым текстом
и движущимся таймкодом, затем экспорт H.264 в MP4. `ffprobe` подтвердил
1920×1080, 30 fps, 98 кадров и 3.266667 с (клип начинается на восьмом кадре).
Кадр готового файла декодирован отдельно: текст присутствует.

Пик памяти всего runtime-cgroup — **841 396 224 байта (802.4 MiB)**;
сюда входят приложение, Xvfb, снимки экрана, вспомогательные процессы,
файловый кеш и предыдущие попытки запуска этой среды. RSS приложения после
экспорта — 243 088 KiB, максимальный RSS — 687 024 KiB. Все счётчики
`memory.events`, включая `oom` и `oom_kill`, равны нулю. Это измерения
короткого текстового проекта, а не предел памяти любого монтажа.

Скриншоты, проверочный бинарник, экспорт и лог сохранены локально в
`target/verification/freecut-linux-*`; основные параметры и `ffprobe`
включены в `performance-results.json`. Тестовый контейнер удалён после
сохранения результатов. Физического аудиоустройства в нём нет: проверено
продолжение работы без звука, вывод звука здесь не проверялся.

Так подтверждены запуск, базовое редактирование, превью и экспорт целиком
на CPU в лимите меньше 2 ГБ. Старый физический Intel/AMD, Windows WARP,
длинные видеопроекты и сложные эффекты этим тестом не проверены. Контейнер
работал на современном M3 Pro; квота CPU не эмулирует скорость старого CPU
или расходы полноценной ОС на машине с 2 ГБ общей RAM.

## Границы совместимости

Windows x64 пакет собран и проверен через WARP, включая запуск portable,
установку и запуск установленной копии с лимитом 1536 MiB commit процесса.
На Windows также прошли 121 тест рендера и 13 e2e. Размер установленного
пакета — 207.9 MB, EXE-установщика — 57.6 MB. Подробные метрики, состав и
границы проверки приведены в [packaging.md](packaging.md). Windows 7/8 и
физический старый ПК этим выпуском не проверены.

- Проверка на старом Intel/AMD CPU и его программном графическом драйвере пока не
  выполнена. Сборки используют базовый набор инструкций целевой архитектуры,
  без `target-cpu=native` и без обязательного AVX2. Физический тест на целевых
  Windows/Linux/macOS машинах всё равно нужен.
- Исходная и оптимизированная macOS-сборки с cpal 0.18.2 имеют сильные ссылки
  на `AudioHardwareCreateProcessTap` и `AudioHardwareDestroyProcessTap`.
  Поэтому `minos 11.0` в заголовке исполняемого файла не подтверждает запуск
  на macOS 11–14.1. Это известный предел аудиозависимости, описанный также в
  `architecture/README.md` §5.14. В этой работе cpal не подменялся.
- Исходная release-сборка использует библиотеки по путям Homebrew. Добавленный
  [упаковщик macOS](packaging.md) переносит их внутрь `.app` и создаёт DMG.
  Текущий пакет arm64 требует macOS 15.0 из-за минимума этих библиотек;
  нижняя версия ОС отдельно не проверялась. Размер `.app` — 73.8 MB,
  DMG — 35.0 MB. Это локальная ad-hoc сборка без нотарификации Apple.
- Превью и экспорт сейчас компонуются на CPU. GPU-композитор и аппаратный
  decode/proxy pipeline остаются отдельными задачами. Производительность
  сложного 4K-монтажа на старом двухъядерном CPU не гарантируется.
- 64 MiB — лимиты двух конкретных кешей, а не всего процесса. Рабочие кадры,
  FFmpeg reference frames, аудио, текст, LUT и текстуры UI требуют память
  сверх этих лимитов. Память одновременно видимых слоёв не выбрасывается.
